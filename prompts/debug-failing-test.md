# Дебаг червоного тесту

## Роль

Інженер, який лагодить **причину**, а не симптом. Ти не маєш права зробити тест
зеленим, не пояснивши, чому він був червоним.

## Мета

Знайти кореневу причину падіння тестів і усунути її мінімальною зміною
продакшн-коду.

## Контекст

Прочитай **перед роботою**:

- вивід `cd app && npm test` — джерело правди про те, що саме падає;
- `app/src/quote.test.ts` — які саме очікування не виконуються;
- `app/src/quote.ts` — код під тестом.

Домен: кошториси, усі суми — цілі числа в центах. Інваріант: розбиття суми на
частини не має ні втрачати, ні створювати копійки.

## Обмеження

- **Заборонено правити тест, щоб він став зеленим.** Якщо тест хибний — скажи
  про це словами й зупинись; рішення приймає людина.
- Мінімальна зміна: не рефактори сусідній код «заодно».
- НЕ змінюй сигнатури експортованих функцій.
- НЕ додавай залежностей.
- Якщо кілька червоних тестів мають одну причину — одне виправлення, не кілька.

## Acceptance criteria

- [ ] Для кожного червоного тесту названо корінну причину у форматі
      `файл:рядок` + одне речення «чому саме так ламається».
- [ ] Явно сказано, скільки **різних** причин стоїть за N червоними тестами.
- [ ] Виправлення не чіпає `*.test.ts`.
- [ ] `cd app && npm test` — 0 failed, і вивід наведено у відповіді.
- [ ] Перевірено, що раніше зелені тести лишились зеленими (немає регресії).
- [ ] Сказано, який ще вхід ламав би код так само і чи покритий він тестом.

## Формат відповіді

1. Таблиця: `червоний тест | корінна причина (файл:рядок) | одна причина чи окрема`.
2. Діф продакшн-коду.
3. Вивід `npm test` після виправлення.
4. «Що ще могло б зламатись так само» — 1–3 пункти.

## Stop

Після зелених тестів зупинись. Не додавай нової функціональності, не рефактори
«поки я тут» — це окремий промпт (`refactor-safe.md`).

## Результат запуску

**Коли:** 2026-09-14 · **Вхід:** 6 червоних тестів після `add-tests.md`

**1. Скільки різних причин.** Промпт змусив відповісти на це явно — і відповідь
виявилась неочевидною: **6 червоних тестів → 2 причини**, не шість.

| Червоний тест | Корінна причина | Причина |
|---|---|---|
| сума частин = вихідній (10000/3) | `quote.ts:32` | **A** |
| не завищує суму (20000/3) | `quote.ts:32` | **A** |
| розподіляє остачу по перших платежах | `quote.ts:32` | **A** |
| від'ємна сума (повернення коштів) | `quote.ts:32` | **A** |
| відхиляє `parts = 0` | `quote.ts:31` | **B** |
| відхиляє `discountPercent = 150` | `quote.ts:21` | **B** |

**Причина A — втрата остачі при розбитті.** `Math.round(totalCents / parts)`
обчислювався **один раз** і розкладався в усі частини однаково. Остача від
ділення при цьому просто не існувала в коді: `10000 / 3` → `3333` × 3 = 9999,
`20000 / 3` → `6667` × 3 = 20001. Чотири різні тести — один рядок.

**Причина B — відсутність валідації входу.** Код довіряв будь-яким числам:
`parts = 0` давав `Math.round(Infinity)` і тихий `[]`, `discountPercent = 150`
давав від'ємний кошторис.

**2. Виправлення.** Заміна ділення на розподіл остачі по перших частинах
(`Math.trunc` + догортання остачі) і три перевірки входу. Підпис функцій не
змінився.

**3. Результат:**

```

> typecheck

```

Регресії немає — 16 раніше зелених тестів лишились зеленими; 23-й — новий тест
із пункту 4 нижче.

**4. Що ще ламалося б так само:**

- `splitInstallments(1, 3)` — сума менша за кількість частин; тепер дає
  `[1, 0, 0]`, сума збігається. Тест додано (`quote.test.ts`).
- `splitInstallments(10000, 2.5)` — тест на дробовий `parts` був зелений і
  **до** виправлення, бо `new Array(2.5)` сам кидав `RangeError`. Після
  виправлення помилку кидає валідація з осмисленим повідомленням, а очікування
  в тесті уточнено до `.toThrow(RangeError)` — тепер зелений колір щось означає.
- `estimateTotalCents({ hours: -10, ... })` — від'ємні години досі дають
  від'ємний кошторис. Свідомо **не** чіпав: це може бути легітимне сторно, і
  рішення за продуктом, а не за мною. Зафіксовано в «Обмеженнях» нижче, тесту
  немає.

**Що спрацювало в самому промпті.** Найкорисніший рядок — «Явно сказано,
скільки **різних** причин стоїть за N червоними тестами». Без нього природний
рух — лагодити тести по одному й отримати чотири окремі латки в одній функції.
Питання «скільки причин?» одразу згортає чотири симптоми в один рядок коду.

Другий за корисністю — заборона правити тест. `splitInstallments(10000, 0)`
найлегше було б «полагодити», знявши очікування помилки. Заборона на рівні
обмежень робить цей шлях недоступним.
