# Безпекове рев'ю дифу перед пушем

## Роль

Інженер, що відповідає за те, щоб у публічний репозиторій не поїхало зайве.
Ти не рев'юєш архітектуру й не шукаєш баги — для цього є
[`review-pr.md`](./review-pr.md). Ти шукаєш **витік**.

## Мета

Перевірити всі зміни гілки на наявність секретів, PII, клієнтських даних і
небезпечних патернів — до того, як вони стануть публічною історією git.

## Контекст

Прочитай **перед роботою**:

- `git diff --stat origin/main...HEAD` — обсяг змін;
- `docs/sanitization-checklist.md` §1–2 — класифікація, патерни пошуку і
  **готовий NUL-безпечний сніпет** збору списку файлів із контролем дійсності;
  бери його звідти, не винаходь свій;
- `.gitignore` — що вже виключено.

Перевіряються **і відстежені зміни, і невідстежені файли**
(`git ls-files -z --others --modified --exclude-standard`): `.env`, дампи й
тимчасові вигрузки найчастіше саме серед невідстежених.

**Ключове припущення, яке треба спростувати, а не прийняти:** «у мене секретів
немає». Перевіряється командами, не відчуттям.

## Обмеження

- **Не виправляй нічого сам.** Спершу список знахідок → рішення людини.
- Не коментуй стиль, архітектуру, форматування й іменування — не твоя задача.
- Не пропускай знахідку тому, що значення «виглядає тестовим»: `fake`-префікс
  треба **довести**, а не припустити.
- Перевіряй і **невідстежені** файли (`git status`), не лише діф: `.env`,
  дампи й тимчасові файли найчастіше саме там.
- Перевіряй **історію**, а не лише поточний стан: секрет, доданий і видалений
  у межах гілки, лишається в комітах.
- **Не фільтруй вивід перевірки** (`| rg -v ...`, `| grep -v ...`). Фільтр не
  відрізняє згадку слова «token» у тексті від справжнього токена поруч. Шум
  читається очима — інакше чистий вивід означає лише те, що ти його почистив.

## Acceptance criteria

- [ ] Список файлів зібрано **NUL-безпечно** в масив (`git diff -z` +
      `git ls-files -z`, `read -r -d ''`) і передається як `-- "${files[@]}"`.
      `$(cat files.txt)` не годиться: розбиває шляхи за пробілами, розгортає
      glob, а шлях із `-` на початку стає опцією `rg`.
- [ ] Перевірено, що масив **не порожній**, до першого виклику `rg`. Порожній
      масив зникає з командного рядка, і `rg` сканує весь поточний каталог —
      даючи ненульове `files searched` не по тих файлах.
- [ ] **Контроль дійсності перевірки:** `rg --stats --only-matching --replace ''
      '' -- "${files[@]}"` дає `files searched`, що дорівнює `${#files[@]}`.
      `--replace ''` обов'язковий: без нього порожній патерн зіставляється з
      кожним рядком і весь вміст документів тече у вивід. Без цього рядка
      результат перевірки не зараховується.
- [ ] Увімкнено `set -o pipefail` (або код виходу першого `rg` збережено
      окремо): інакше `rg … | rg 'files searched'` поверне `0`, навіть якщо
      перший `rg` упав.
- [ ] Прогнано всі патерни з `sanitization-checklist.md` §2 по цьому списку;
      команди й **повний** вивід наведено (код виходу `>1` = провалена перевірка,
      не «чисто»).
- [ ] Перевірено, що `.env` та інші ігноровані файли **справді** не в індексі:
      `git ls-files | rg '\.env'` порожній.
- [ ] Перевірено історію гілки: `git log -p origin/main...HEAD | rg '<патерни>'`.
- [ ] Для кожного файлу з `docs/` сказано, чи містить він дослівні значення з
      `materials/client-brief.md` (звірка, а не «на око»).
- [ ] Кожна знахідка має: `файл:рядок` | категорія 🔴/🟡 | чому це проблема |
      що зробити.
- [ ] Явно сказано, **чи є знахідки категорії 🔴** — окремим рядком «так/ні».
- [ ] Якщо знахідок немає — так і написано, без вигаданих зауважень.

## Формат відповіді

1. Команди та їхній вивід (як є).
2. Таблиця знахідок: `файл:рядок | 🔴/🟡 | проблема | дія`.
3. Рядок-вердикт: `🔴 знахідок: N` — і чи можна пушити.
4. «Що ця перевірка не покриває» — межі методу.

## Stop

Після вердикту зупинись. Виправлення — окремим запитом; пуш — рішення людини.

### 1. Команди та вивід (відтворювані дослівно)

```bash
set -o pipefail

# список файлів гілки — NUL-безпечно, у масив
files=()
while IFS= read -r -d '' f; do files+=("$f"); done < <(
  { git diff -z --name-only origin/main...HEAD
    git ls-files -z --others --modified --exclude-standard; } | sort -zu
)
(( ${#files[@]} )) || { echo "ПРОВАЛ: список файлів порожній"; exit 2; }
```

```
$ echo "${#files[@]}"
16
```

**Контроль дійсності** — без нього вивід нижче нічого не означає
(`--replace ''` гасить вміст, щоб порожній патерн не злив документи у транскрипт):

```
$ stats=$(rg --stats --only-matching --replace '' '' -- "${files[@]}"); echo $?
0
$ grep 'files searched' <<<"$stats"
16 files searched          ← дорівнює ${#files[@]}, перевірка дійсна
```

### 4. Що ця перевірка НЕ покриває

- **Бінарні файли, зображення, PDF** — у гілці їх немає, патерни їх не читають.
- **Дані, чутливі в сукупності** — окремо нешкідливі факти, що разом
  ідентифікують клієнта. Судження людини, не regex.
- **Семантику плейсхолдера.** `<N8N_URL_OUT_OF_BAND>` проходить перевірку, але
  чи справді за ним немає значення десь поруч — regex не скаже.

### Оцінка самого промпта

**Найцінніший критерій — той, що змусив перевірити власний результат, а не
лише вхідні матеріали.** Обидві знахідки — у файлі, який я щойно написав як
*безпековий звіт*. Це найкращий аргумент за окремий прохід рев'ю: автор
документа про ін'єкції на автопілоті вставив у нього робочу ін'єкцію, бо був
зосереджений на змісті, а не на тому, хто цей файл читатиме далі.

**Що спрацювало гірше — і це найважливіше в усьому прогоні.**

Перевірка **тричі поспіль збрехала мені «чисто»**, і щоразу з іншої причини:

1. **Фільтр.** Я відфільтрував вивід через `rg -v 'KEY|TOKEN|SECRET'`, щоб
   прибрати згадки цих слів у тексті правил — і разом із шумом вирізав усе.
2. **Розщеплення слів у zsh.** `rg -n "$pat" $FILES` у bash розбило б `$FILES`
   на 16 аргументів, а zsh передає його **одним** рядком. `rg` шукав файл з
   іменем у 16 рядків, падав з `IO error`, а `|| echo '(нічого)'` перетворював
   збій на слово «нічого». Контрольний прогін пізніше показав `0 bytes searched`.
3. **Придушений stderr.** `2>/dev/null` сховав `xargs: rg: No such file or
   directory` (код 127): `rg` тут — аліас оболонки, і `xargs` його не бачить.

У всіх трьох випадках екран виглядав **однаково** — «(нічого)». І в усіх трьох
випадках правильний висновок був «перевірка не відбулася», а не «чисто».
Дійсну знахідку (🔴 PII у власному чек-лісті) знайшов лише четвертий,
коректний прогін.

Звідси два записи, які пішли в артефакти:

- в «Обмеження» цього промпта — заборона фільтрувати вивід (v1 → v2);
- у `docs/sanitization-checklist.md` §2 — обов'язковий **контрольний прогін**
  `rg --stats --only-matching --replace '' '' -- "${files[@]}"` перед довірою
  до результату, плюс правило трактувати код виходу `>1` як провалену перевірку.

**Друге рев'ю CodeRabbit добило те саме місце ще на три рівні глибше** — і всі
три зауваження були по суті:

- `$(cat files.txt)` сам по собі небезпечний: розбиває шляхи за пробілами,
  розгортає glob, а шлях із `-` на початку `rg` прийме за опцію. Виправлено на
  NUL-безпечний масив.
- **Порожній список файлів** мовчки перетворює перевірку на сканування всього
  каталогу — з бадьорим ненульовим `files searched`. Тобто контроль, який я
  додав проти хибного «чисто», сам міг дати хибне «перевірено». Додано гард.
- Контрольна команда з порожнім патерном `''` зіставляється з **кожним рядком**,
  тож весь вміст документів тік у вивід і транскрипт. Виправлено
  `--only-matching --replace ''`.

Тобто перевірка, яку я писав саме щоб ловити витоки, на трьох ітераціях сама
була то сліпою, то дірявою. Це найкращий аргумент за те, що безпекові скрипти
потребують рев'ю нарівні з продакшн-кодом — «це ж просто grep» тут не працює.

**Ширший висновок.** Для безпекової перевірки «нічого не знайдено» — це не
результат, а гіпотеза. Результатом вона стає лише разом із доказом, що сканер
справді читав те, що мав. Саме тому в acceptance criteria тепер стоїть
контроль кількості просканованих файлів, а не лише «прогнано патерни».

Показово й те, що **всі чотири знахідки — у моїх власних щойно написаних
документах**, не у вхідних матеріалах: реальний URL продакшн-інстансу,
телефон із брифу, двічі відтворений payload. Автор не бачить цього за собою,
бо думає про зміст, а не про те, хто читатиме файл далі.
