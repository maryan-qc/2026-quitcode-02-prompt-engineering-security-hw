# Додати тести на крайові випадки

## Роль

Senior TypeScript-розробник, який пише тести, щоб **знаходити дефекти**, а не
щоб підняти цифру покриття. Зелений тест, що нічого не перевіряє, — це шкода.

## Мета

Розширити тестовий файл крайовими випадками так, щоб кожна функція модуля
мала перевірку на межах діапазону, і зафіксувати тестом кожен знайдений дефект.

## Контекст

Прочитай **перед роботою**:

- `app/src/quote.ts` — модуль під тестом (функції `estimateTotalCents`,
  `splitInstallments`, `formatMoney`).
- `app/src/quote.test.ts` — наявні тести (happy path, свідомо неповні).
- `app/package.json` — раннер `vitest`, команда `npm test`.

Домен: розрахунок кошторисів. **Усі суми — цілі числа в центах.** З цього
випливає інваріант, який треба перевірити явно: сума частин розбиття мусить
дорівнювати вихідній сумі до копійки.

Робочий каталог для команд: `app/`.

## Обмеження

- НЕ змінюй сигнатури експортованих функцій і не перейменовуй експорти.
- НЕ додавай залежностей у `package.json` — лише наявний `vitest`.
- НЕ чіпай файли поза `app/src/`.
- Не «підганяй» тест під поточну поведінку: якщо поведінка хибна — тест має
  падати, а виправлення йде **окремим кроком** після мого підтвердження.

## Acceptance criteria

- [ ] Для кожної з трьох експортованих функцій є щонайменше один тест на межі.
- [ ] Явно перевірено: `0`, від'ємні значення, дробовий результат ділення,
      округлення, відсутній необов'язковий параметр.
- [ ] Є тест на інваріант «сума частин = вихідна сума» для випадку, що **не**
      ділиться націло (напр. `10000 / 3`).
- [ ] Кожен тест має назву, з якої видно **очікувану поведінку**, а не назву функції.
- [ ] `cd app && npm test` виконано, і його вивід наведено у відповіді.
- [ ] Якщо якийсь тест червоний — названо файл:рядок і конкретний вхід, що ламає.

## Формат відповіді

1. Список крайових випадків, які збираєшся покрити (до написання коду).
2. Діф `app/src/quote.test.ts`.
3. Вивід `npm test` як є.
4. Окремий розділ «Знайдені дефекти»: `файл:рядок | вхід | очікувано | фактично`.

## Stop

Зупинись після виводу тестів і списку дефектів. **Не виправляй продакшн-код** —
виправлення замовляється окремим промптом (`debug-failing-test.md`).

**Коли:** 2026-09-14 · **Інструмент:** Claude Code (Opus 5) · **Команда:** `cd app && npm test`

Промпт запущений на `app/src/quote.ts`. Покриття виросло з **4 до 22** тестів,
з них **6 червоних** — і всі шість вказують на реальні дефекти, а не на мої
хибні очікування:

```

 AssertionError: expected 20001 to be 20000

 AssertionError: expected [ 3333, 3333, 3333 ] to deeply equal [ 3334, 3333, 3333 ]
 FAIL  splitInstallments > працює з від'ємною сумою (повернення коштів)
 AssertionError: expected -9999 to be -10000
 FAIL  splitInstallments > відхиляє нульову кількість частин замість тихого порожнього масиву
 AssertionError: expected [Function] to throw an error
 FAIL  estimateTotalCents > відхиляє знижку поза діапазоном 0..100
 AssertionError: expected [Function] to throw an error
```

**Знайдені дефекти:**

| # | Місце | Вхід | Очікувано | Фактично |
|---|---|---|---|---|
| 1 | `app/src/quote.ts:32` | `splitInstallments(10000, 3)` | сума частин = 10000 | 9999 — копійка зникла |
| 2 | `app/src/quote.ts:32` | `splitInstallments(20000, 3)` | сума частин = 20000 | 20001 — клієнта перерахували |
| 3 | `app/src/quote.ts:32` | `splitInstallments(10000, 0)` | помилка | тихо `[]` |
| 4 | `app/src/quote.ts:21` | `discountPercent: 150` | помилка | `-25000`, від'ємний кошторис |

Дефект №1 — це і є та закладена вада, про яку попереджає `materials/weak-prompt.md`.
Причина одна на всі три перші рядки: `Math.round(totalCents / parts)` рахується
**один раз** і розкладається у всі частини однаково, тож остача від ділення
або зникає, або множиться.

**Цікаве спостереження:** тест «відхиляє дробову кількість частин»
(`splitInstallments(10000, 2.5)`) — **зелений, але з неправильної причини**.
Валідації немає; просто `new Array(2.5)` сам кидає `RangeError: Invalid array
length`. Тобто зелений тест тут нічого не гарантує — варто було б перевіряти тип
помилки, а не сам факт кидка.

**Що довелось поправити в самому промпті (v1 → v2).** Перша версія просила
«покрити крайові випадки» загальними словами. Цього мало: крайовим випадком
природно вважаєш `0`, від'ємне і порожній вхід — а дефект тут ховається не на
межі діапазону, а в **арифметиці ділення**. Доказ під рукою: базовий тест зі
стартового репо (`splitInstallments(90000, 3)`) — теж про розбиття, теж
проходить, і саме тому вади не бачить: 90000 ділиться націло.

У v2 додав два конкретні рядки в acceptance criteria — «дробовий результат
ділення» і «інваріант «сума частин = вихідна сума» для випадку, що **не**
ділиться націло (напр. `10000 / 3`)». Після цього дефект ловиться з першого
прогону. Урок: AC мусить називати **інваріант домену**, а не категорію тестів.
«Покрий крайові випадки» — це побажання, «сума частин дорівнює вихідній сумі» —
це критерій, на який можна відповісти «так/ні».

**Stop-правило спрацювало:** на шести червоних тестах агент зупинився і не поліз
правити `quote.ts` самовільно — виправлення пішло окремим промптом
[`debug-failing-test.md`](./debug-failing-test.md).

## Той самий промпт у XML-діалекті

Той самий зміст, інша упаковка — для моделей, що краще тримають структуру на тегах:

```xml
<task>Розширити тестове покриття до крайових випадків і знайти приховані дефекти</task>
<role>Senior TypeScript-розробник; тести пишуться, щоб знаходити дефекти, а не піднімати % покриття</role>
<context>
  <target>app/src/quote.ts</target>
  <tests>app/src/quote.test.ts</tests>
  <runner>vitest — `cd app &amp;&amp; npm test`</runner>
  <domain>Кошториси; усі суми — цілі числа в центах</domain>
  <invariant>Сума частин розбиття = вихідна сума, до копійки</invariant>
</context>
<constraints>
  <no>міняти сигнатури експортованих функцій</no>
  <no>додавати залежності</no>
  <no>чіпати файли поза app/src/</no>
  <no>підганяти тест під поточну поведінку</no>
</constraints>
<acceptance>
  <item>кожна з трьох функцій має тест на межі</item>
  <item>перевірено: 0, від'ємні, дробовий результат ділення, округлення, відсутній опційний параметр</item>
  <item>є тест на інваріант суми для випадку, що не ділиться націло (10000 / 3)</item>
  <item>назва тесту описує очікувану поведінку, не назву функції</item>
  <item>вивід `npm test` наведено у відповіді</item>
  <item>для кожного червоного тесту названо файл:рядок і вхід, що ламає</item>
</acceptance>
<format>
  1. список крайових випадків до написання коду
  2. діф app/src/quote.test.ts
  3. вивід npm test як є
  4. таблиця дефектів: файл:рядок | вхід | очікувано | фактично
</format>
<stop>Після списку дефектів зупинись. Продакшн-код НЕ виправляй.</stop>
```

### Чи відчув різницю між діалектами

**Спершу про межі цієї перевірки, щоб не видавати бажане за факт.** Реально
прогнано на задачі **markdown-версію** — саме її результат наведено вище.
XML-версія — переклад того самого змісту, і я перечитав її на предмет
повноти, але **чистого A/B у двох незалежних сесіях я не робив**. Тому нижче —
тільки те, що видно з самого написання артефактів, без вигаданих цифр про
«модель повелася інакше».

Що видно напевно:

- **Зміст важить більше за розмітку.** Дефект знайшов не формат, а один рядок
  в acceptance criteria — інваріант «сума частин = вихідна сума». Прибери його
  з будь-якої з двох версій, і обидві пройдуть повз ваду: доказ під рукою — у
  стартовому репо вже був тест на `splitInstallments`, і він зелений, бо
  `90000 / 3` ділиться націло. Переписування markdown → XML тут не змінило б
  нічого.
- **XML жорсткіше задає форму відповіді.** `<format>` з чотирма пунктами —
  це перелік слотів, які видно як незаповнені. У markdown «Формат відповіді» —
  це абзац, який легше проігнорувати частково. Для промптів, чию відповідь
  парсить скрипт, це аргумент за XML.
- **XML дорожчий у супроводі, і це вимірюється.** Той самий промпт: markdown —
  ~40 рядків, XML — ~30, але XML треба екранувати (`cd app &amp;&amp; npm test`),
  і одна забута `&` ламає структуру мовчки. Для файлу, який редагує вся
  команда, це реальна вартість.

**Висновок для команди:** тримаємо промпти в markdown; у XML перекладаємо лише
ті, що викликаються автоматизацією і чию відповідь читає машина, а не людина.

**Що лишилось неперевіреним:** чи дає XML стабільніший вихід на слабших
моделях. Це перевіряється тільки прогоном обох версій у чистих сесіях на
кількох моделях — окрема задача, не встиг у межах цієї домашки.
