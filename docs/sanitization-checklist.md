# Чек-ліст санітизації даних перед роботою з AI

**Для кого:** усі, хто дає моделі будь-який текст клієнта — бриф, лист, лог,
скрін, дамп, JSON воркфлоу.
**Коли застосовувати:** щоразу перед першою вставкою матеріалу в модель, а не
«коли схоже на чутливе».
**Скільки займає:** 5–10 хвилин на документ. Якщо довше — документ занадто
великий, ріжте на частини.

Приклад застосування на реальному документі: [`sanitized-brief.md`](./sanitized-brief.md).

---

## 0. Головне правило

> Санітизуємо **локально**. Оригінал у публічну модель не потрапляє **ніколи** —
> зокрема й «щоб вона сама його почистила». Модель, яку просять замаскувати
> секрет, спершу його **прочитала**; з цього моменту секрет вважається
> скомпрометованим, а маскування — театром.

Друге за важливістю: санітизація — це **зменшення радіуса ураження**, а не
гарантія. Вона не скасовує ні NDA, ні потреби в правильному тирі інструмента.

## 1. Класифікація: світлофор

| Категорія | Що сюди входить | Куди можна |
|---|---|---|
| 🔴 **Секрети** | API-ключі, токени, PAT, паролі, connection strings, приватні ключі, credentials з n8n/CI, сесійні кукі, JWT | **нікуди.** Тільки out-of-band через env |
| 🔴 **PII** | ПІБ, email, телефон, адреса, месенджер, ЄДРПОУ/ІПН, номери документів, геолокація | **нікуди** в публічну модель |
| 🔴 **Продакшн-дані** | вигрузки таблиць, логи із запитами користувачів, стек-трейси з даними, скріни з реальними записами | **нікуди.** Замінити синтетикою |
| 🟡 **Комерція** | ставки, собівартість, маржа, умови угод, дедлайни пропозицій, згадки конкурентів | лише enterprise / no-train (див. §5) |
| 🟡 **Внутрішня логіка** | назви вендорів і внутрішніх систем, схеми БД, назви гілок і сервісів, внутрішні URL | лише enterprise / no-train |
| 🟢 **Постановка** | опис проблеми, послідовність кроків, критерії приймання, обсяги без даних, формати полів | будь-яка модель |

**Правило тиру:** документ належить до **найвищої** категорії, яка в ньому є.
Один токен у додатку робить 🔴 весь пакет.

**Спірні випадки — вирішувати так:**

- Назва компанії-клієнта у зв'язці з фактом «шукає підрядника» — 🔴, бо це
  комерційно чутливо навіть без PII.
- ID записів (`appXXXX`, `wf_123`) — 🟡: самі по собі не відкривають доступ,
  але дають карту внутрішнього ландшафту.
- Скріншот — за найгіршим, що на ньому видно, **включно з таббаром браузера й
  сповіщеннями**.

## 2. Як шукати (а не «уважно перечитати»)

Прогнати по документу/каталогу перед відправкою:

Прогнати по документу/каталогу перед відправкою (патерни звірені на
`materials/client-brief.md` — ловлять там усі 3 рядки з ключами, обидва email,
усі 4 телефони й усі 3 адреси):

```bash
# 1. секрети за словом
rg -ni 'api[ _-]?key|secret|token|passwo?rd|bearer|authorization|credential|\bPAT\b' PATH

# 2. connection strings
rg -n 'postgres://|mysql://|mongodb(\+srv)?://|redis://|amqp://' PATH

# 3. секрети за формою значення
rg -n 'xox[baprs]-|sk-[A-Za-z0-9]{16,}|ghp_[A-Za-z0-9]{36}|pat[A-Za-z0-9.]{14,}|AKIA[0-9A-Z]{16}' PATH
rg -n -- '-----BEGIN [A-Z ]*PRIVATE KEY-----' PATH

# 4. email
rg -n '[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}' PATH

# 5. телефон UA
rg -n '\+?380[\s\-()]*\d{2}[\s\-()]*\d{3}[\s\-]*\d{2}[\s\-]*\d{2}' PATH

# 6. адреси
rg -ni 'вул\.|просп\.|м\. [А-ЯІЇЄҐ]' PATH
```

> ⚠️ **Патерни самі потребують перевірки — і перші дві версії цих були
> дірявими.** Перевірено запуском на `materials/client-brief.md`:
>
> - `api[_-]?key` **пропускав** рядок `| CRM API key |`, бо між словами
>   пробіл, а не `_`. Виправлено на `api[ _-]?key`, додано `\bPAT\b`.
> - Телефонний патерн не знайшов **жодного** справжнього телефону у форматі
>   `+380 (NN) NNN-NN-NN`: після коду країни там два роздільники (пробіл і
>   дужка), а патерн допускав один. Зате видавав за телефони цифри всередині
>   Slack-токена. Тобто він був одночасно сліпий і шумний — найгірше поєднання,
>   бо з непорожнім виводом виглядав робочим.
>
> **Правило:** перш ніж довіряти патерну, прогнати його на документі, де
> чутливе завідомо є, і **перерахувати знахідки руками**. Порожній вивід
> означає «патерн не спрацював» рівно так само часто, як «чисто».

### Контрольна перевірка: чи сканер узагалі щось читав

Порожній вивід має **чотири** причини, і лише одна з них добра: чисто, поганий
патерн, сканер не отримав файлів або сканер узагалі не запустився. Тому список
файлів будуємо NUL-безпечно, а перед скануванням робимо контрольний прогін.

```bash
set -o pipefail          # інакше код помилки першої команди в пайпі губиться

# 1. Список файлів — через NUL, а не через пробіли.
#    Захищає від: пробілів і лапок у шляхах, glob-розгортання, і від шляху,
#    що починається з "-" (його rg прийняв би за опцію).
files=()
while IFS= read -r -d '' f; do files+=("$f"); done < <(
  { git diff -z --name-only origin/main...HEAD
    git ls-files -z --others --modified --exclude-standard; } | sort -zu
)

# 2. Порожній список — це ПРОВАЛ перевірки, а не «чисто".
#    Без цієї перевірки "${files[@]}" зникає з рядка, і rg сканує ВЕСЬ
#    поточний каталог — даючи бадьоре "files searched" не по тих файлах.
(( ${#files[@]} )) || { echo "ПРОВАЛ: список файлів порожній"; exit 2; }

# 3. Контроль: скільки файлів rg реально відкрив.
#    --only-matching --replace '' гасить ВМІСТ: інакше порожній патерн ''
#    зіставляється з кожним рядком і весь документ тече у вивід і транскрипт.
stats=$(rg --stats --only-matching --replace '' '' -- "${files[@]}"); rc=$?
(( rc > 1 )) && { echo "ПРОВАЛ: rg завершився з кодом $rc"; exit 2; }
grep 'files searched' <<<"$stats"
#   → 16 files searched   ✓ і має дорівнювати ${#files[@]}
#   → 0 files searched    ✗ сканування не відбулося, вивід нічого не означає
```

Далі всі патерни ганяємо по тому самому масиву: `rg -n '<патерн>' -- "${files[@]}"`.

**Граблі, на які це ловить — усі чотири траплялися при роботі над цим репо:**

| Пастка | Симптом | Як правильно |
|---|---|---|
| **zsh не розбиває `$FILES` на слова** (на відміну від bash) | `rg` отримує весь список як одне ім'я файлу → `IO error`, `0 bytes searched` | масив + `-- "${files[@]}"` |
| **`$(cat files.txt)` розбиває за пробілами й розгортає glob** | шлях із пробілом «розпадається» на два; шлях із `-` стає опцією `rg` | `git ls-files -z` + `read -d ''` |
| **`2>/dev/null` ковтає помилку запуску** | `command not found` не видно, лишається «нічого не знайдено» | не придушувати stderr; перевіряти код виходу |
| **код виходу губиться в пайпі** | другий `rg` повертає `0`, хоча перший упав з `2` | `set -o pipefail` або зберігати `rc` окремо |

**Головне:** `rg` повертає `1` і коли збігів немає — візуально це те саме, що
й збій. Для безпекової перевірки **код виходу `>1` = провалена перевірка**,
а не «чисто».

> **Якщо в команді немає ripgrep.** Він не входить у macOS; у нас він був
> доступний лише як шим усередині Claude Code. Той самий контроль на `grep`:
> `grep -rlE '<патерн>' -- "${files[@]}" | wc -l`, а замість `--stats` —
> порівняння `${#files[@]}` з кількістю успішно відкритих файлів
> (`for f in "${files[@]}"; do [ -r "$f" ] || echo "НЕЧИТАЄТЬСЯ: $f"; done`).

Що це **не** ловить — перевіряти очима:

- секрет, записаний словами («пароль — назва компанії й рік»);
- PII у зображеннях, PDF-сканах і скріншотах;
- чутливе в **історії файлу**: `git log -p`, коментарі, `Track Changes` у .docx,
  метадані EXIF;
- дані, що стають чутливими в сукупності (посада + місто + вік = конкретна людина).

## 3. Як маскувати

| Техніка | Коли | Приклад |
|---|---|---|
| **redaction** — прибрати | значення не потрібне для задачі взагалі | маржа → `<INTERNAL>` |
| **masking** — лишити форму, прибрати значення | важливий формат (валідація, парсинг) | `+380 (XX) XXX-XX-XX`, `****-1234` |
| **pseudonymisation** — стабільний плейсхолдер | сутність згадується кілька разів і зв'язки важливі | `[CLIENT_1]`, `[CONTACT_1]`, `S1..S5` |
| **synthetic** — вигадати правдоподібне | потрібні дані для прикладу/тесту | 3 рядки того ж формату з `[SYNTHETIC_*]` |
| **out-of-band** — не в текст узагалі | будь-який секрет | `<SECRET_OUT_OF_BAND>` + env на запуску |

**Три правила, які найчастіше порушують:**

1. **Плейсхолдери мають бути стабільні.** Одна людина = один `[CONTACT_1]` по
   всьому документу. Інакше модель вирішить, що це різні люди, і зламає логіку.
2. **Синтетика має зберігати крайові випадки.** Якщо в реальних даних є
   юрособа без ПІБ із трьох слів або адреса без квартири — синтетичні рядки
   мусять це відтворювати, інакше спроєктована валідація впаде на проді.
3. **Маскувати рівно до межі задачі.** Контрольне питання перед відправкою:
   **«чи може виконавець, який бачив тільки цей файл, зробити роботу?»**
   Якщо ні — замасковано зайве, і це така сама помилка, як недомасковане.

## 4. Креденшели: окремий режим

Секрети **не маскуються — вони виносяться**. Порядок:

1. У документі на місці значення — `<SECRET_OUT_OF_BAND>`; поруч зазначити
   **клас доступу** (`REST API, ключ`), бо він потрібен для проєктування.
2. Значення лишається там, де вже лежить: менеджер секретів, n8n credential
   store, CI secrets. З документа туди — **посилання на ім'я креденшела**, не
   значення.
3. У виконавче середовище — через змінні оточення на етапі запуску. Не в
   промпт, не в чат, не в файл у репозиторії.
4. Агенту явно заборонено читати `.env` і файли з `KEY|TOKEN|SECRET` у назві —
   див. розділ «Захист від prompt injection» в [`../AGENTS.md`](../AGENTS.md).
5. `.env` і похідні — у `.gitignore`. Перед пушем: `git diff --staged` очима,
   не лише на автопілоті.

**Якщо секрет усе-таки поїхав у модель** — це інцидент, а не незручність:
ротуємо ключ негайно (раніше, ніж пишемо звіт), фіксуємо час і обсяг,
повідомляємо відповідального за інтеграцію. Видалення повідомлення з чату
**не** є мітигацією.

## 5. Категорія → інструмент

| Категорія | Інструмент / режим | Чому саме так |
|---|---|---|
| 🟢 Постановка | звичайна підписка (Claude Code, Cursor) | Немає чого втрачати: постановка задачі не є чутливою |
| 🟡 Комерція, внутрішня логіка | **enterprise / no-train-план із DPA** або локальна модель | Потрібні договірні гарантії, а не налаштування в UI |
| 🔴 Секрети, PII, продакшн-дані | **AI не використовуємо.** Спершу санітизація → документ переходить у 🟢/🟡 | Ризик не компенсується жодним прискоренням |

### Який тир ми беремо для 🟡 і чому

Для 🟡-даних ми беремо **корпоративний план із договірною забороною навчання
на наших даних (no-train) і підписаним DPA**, а не локальну модель і не
«вимкнув історію в налаштуваннях».

Міркування три.

**По-перше, тумблер у налаштуваннях — не зобов'язання.** Перемикач «не
використовувати мої дані для навчання» змінюється продуктовим рішенням
вендора, і ми про це дізнаємось постфактум. Пункт у договорі змінюється лише
підписом обох сторін. Для даних, за які ми відповідаємо перед клієнтом за NDA,
різниця між цими двома станами — це різниця між «ми вжили заходів» і «ми
понадіялись».

**По-друге, потрібні ще три речі, яких споживчий план не дає:** контрольований
строк зберігання (щоб «видалено» означало видалено), журнал доступу (щоб на
питання клієнта «хто бачив наші дані» була відповідь) і адміністративний
контроль над обліковками (щоб доступ зникав разом зі звільненням).

**По-третє, локальна модель вирішує не ту задачу.** Вона прибирає мережевий
ризик — і додає інфраструктуру, оновлення, а головне помітно слабший результат
на задачах, де 🟡-дані й виникають (проєктування інтеграцій, рев'ю коду).
Тримаємо її як запасний варіант для випадків, де клієнтський договір прямо
забороняє передачу даних третій стороні в будь-якому вигляді, — тоді слабший
результат є єдиним доступним.

**🔴 не покриває жоден тир.** Enterprise-план не робить розсилку ключів
безпечною. Для 🔴 працює лише одне: санітизація до 🟢/🟡 **перед** відправкою.

## 7. Де це ще застосовується (найчастіше забувають)

Санітизація стосується не лише документів, які вставляють руками:

- **JSON воркфлоу n8n** — містить URL вебхуків, ID баз, іноді ключі прямо в
  полях вузлів замість credential store.
- **Логи виконання й стек-трейси** — найчастіший канал витоку PII в чат: у
  трейсі лежить payload заявки цілком.
- **Скріншоти** — включно з тим, що видно у вкладках браузера й сповіщеннях.
- **Інструменти агента (MCP).** Коли агент сам ходить в API клієнта, санітизує
  вже не людина. Тут працює не чек-ліст, а **обмеження прав**: доступ лише до
  потрібного, read-only за замовчуванням, підтвердження людини на запис і на
  будь-яку відправку назовні.
